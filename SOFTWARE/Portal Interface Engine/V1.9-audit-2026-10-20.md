## F1 — HIGH — The DC-offset trip reacts far too late to prevent saturation

**Where**

* `V1.9.ino:1571` — `#define DC_TRIP_V          1.0f     // primary DC offset; ~90 ms to saturate`
* `V1.9.ino:2288-2298` — the trip itself
* `V1.9.ino:1962-1976` — `updateRmsAndDc()`, which produces `primaryDc`
* `tests/test_v19_model.py:777-789` — `test_detection_precedes_saturation`

**Why it is wrong**

The "90 ms to saturate" figure predates the Rev C flux re-derivation, which
`AGENTS.md` and `PIE-v1.9-information.md:416-421` both record as putting the
saturation knee at **11–13 ms** at the operating point. The sketch's comment
and the test still use the stale number, and the test's own comment admits it:

```python
# NOTE: the 90 ms figure predates the Rev C flux re-derivation,
# which puts the knee at ~11-13 ms at the operating point.
```

The *actual* detection latency is worse than the test's own 46.64 ms, because
the DC estimate is the mean of the 128-sample ring:

| step | value |
| --- | --- |
| DC estimate window | 128 × 130 µs = **16.64 ms** |
| a step offset of 1.00 V | the mean approaches 1.00 V but **never exceeds it** — the comparison is `fabsf(primaryDc) > DC_TRIP_V`, so an offset of exactly 1.0 V never trips |
| a step offset of 1.01 V | the mean reaches 1.0 V only after ~127 samples = **16.5 ms** |
| debounce | 3 consecutive control ticks = **30 ms** |
| **total** | **≈ 46.5 ms** |

**46.5 ms against an 11–13 ms knee: the transformer is saturated roughly 3.5×
before the firmware reacts.** This is the protection that is supposed to stop
exactly this failure.

The existing test `test_detection_precedes_saturation` asserts
`detect_ms (46.64) < saturation_ms (90)` — it pins a safety property that the
re-derivation has already invalidated, so the suite is green while the
protection is too slow.

**Proposed change** (behaviour change — needs `PIE-v1.9-information.md` and
`AGENTS.md` updated in the same change):

1. shorten the DC window: a dedicated short ring (e.g. 32 samples = 4.2 ms) or
   an IIR for the DC term, instead of reusing the 16.64 ms RMS window;
2. drop the debounce to a single control tick (the estimator itself is already
   filtered);
3. re-derive `DC_TRIP_V` against the 11–13 ms knee and state the margin;
4. rewrite the comment at `:1571` and `:2288-2290` with the re-derived figure.

With a 32-sample window and one tick the latency is ≈ 4.2 + 10 = **14.2 ms**;
with 16 samples and one tick it is ≈ 12.1 ms. Either is inside the knee.

**Tests added**: `tests/test_v19_protection_latency.py` —
`test_the_current_latency_is_characterised` (pins today's 46.65 ms),
`test_the_estimate_cannot_reach_the_threshold_from_a_1v_offset`, and
`test_the_trip_reacts_before_the_saturation_knee` (currently an *expected
failure*, so the gap stays visible and the suite stays green).

## F2 — HIGH — A "set bit" opcode is used to clear a write-1-to-clear bit

**Where**: `V1.9.ino:1884` — `adsSetBits(ADS7128_SYSTEM_STATUS, 0x08)`

**Why it is wrong**

TI SBAS868A Table 12 documents `OSR_DONE` (SYSTEM_STATUS bit 3) as:

> `OSR_DONE` — R/W — **Clear this bit by writing 1b to this bit.**

but §8.5.2.2 documents the opcode the firmware uses (`0x18`, "Set bit") as:

> "Bits with a value of 1 in the register data are **set** and bits with a
> value of 0 in the register data are not changed."

Whether the device implements "set bit" as a hardware set or as a
read-modify-write followed by an ordinary write (in which case the W1C
semantics apply and the bit is cleared) is not stated in the datasheet. The two
readings have very different consequences:

* **clears** → the firmware is correct as written;
* **sets** → `OSR_DONE` stays high, the poll at `V1.9.ino:1881` succeeds
  immediately, and **the result is read before the conversion has completed**.
  Because the sweep is strictly sequential (convert → wait → read → next
  channel), every channel would then report the *previous* channel's value:
  AIN1 (bus) would read the battery rail, AIN2/AIN3 would read the bus and the
  battery, and the current channel would read the last midpoint. That is a
  silent, dangerous data mix-up, not a visible failure.

**Proposed change**

Use the plain single-register write for a W1C bit:

```c
// OSR_DONE is write-1-to-clear (datasheet Table 12), so clear it with a
// plain register write -- the "set bit" opcode (0x18) is documented as
// setting bits, not clearing them.
if (!adsWriteReg(ADS7128_SYSTEM_STATUS, 0x08)) { ... }
```

and add a **bench check**: after clearing, read SYSTEM_STATUS back and confirm
bit 3 reads 0; then convert AIN2, wait, and confirm `RECENT_CH2` tracks the
voltage actually present on AIN2.

## F3 — HIGH — `OSR_DONE` is polled with the averaging filter disabled

**Where**: `V1.9.ino:1868-1899` (the poll), and the absence of any write to
`OSR_CFG`.

**Why it is a risk**

The firmware never writes `OSR_CFG`, so `OSR[2:0]` stays at its reset value
`0b`, which SBAS868A Table 15 defines as **"No averaging"**. The bit it polls,
however, is documented in Table 12 as **"Averaging status … 1b = Averaging
complete; average result is ready"**, and §8.3.6 describes polling `OSR_DONE`
as the way to check *"the averaging completion status"*.

If the device only asserts `OSR_DONE` on the averaging path, then every
conversion times out at the 5 ms limit, `adsPresent` is cleared, `adsSwept`
stays false, `sensorsOk` stays false, and **the inverter can never be armed**.
If it does assert it, the current code is fine. The datasheet does not settle
it, and AGENTS.md already records that the ADS7128 driver is "still
**unverified against silicon**".

**Proposed change / bench check**

1. On the bench, with the bridge disabled: start a conversion, poll
   SYSTEM_STATUS and confirm bit 3 asserts within a few microseconds with
   `OSR_CFG` = 0.
2. If it does not, drop the poll and use the datasheet's simpler manual-mode
   flow, in which the device itself stretches SCL until the conversion
   completes: write `CHANNEL_SEL` (MANUAL_CHID) and then read the result
   registers — no `OSR_DONE`, no `STATS_EN`, no timeout.
3. Either way, record the result in `AGENTS.md` so the next pass does not
   re-derive it.

## F4 — MEDIUM/HIGH — The drive is a 20 kHz PWM, not a 60 Hz sine

**Where**: `V1.9.ino:2093-2110` (`writeBridgeDuty`), the power-stage header
comment at `:1290-1389`, and the transformer-loading comment at `:1583-1593`.

**What the hardware actually produces**

The bridge is a full bridge whose two legs are driven from three slices whose
counters are offset by `dt` and `2·dt` — that is, by 0.5 µs and 1 µs out of a
50 µs carrier. The two legs are therefore *nearly in phase*, and the
differential across the transformer primary is **not** a bipolar square wave at
20 kHz; it is a narrow one-sided pulse train whose average is the commanded
`m · Vbus`.

Re-modelled tick by tick (`tests/test_v19_pwm_waveform.py`):

| modulation | 60 Hz fundamental (RMS) | total waveform (RMS) | ratio |
| --- | --- | --- | --- |
| 0.879 (120 V, no load) | 13.52 V | 20.62 V | 1.53 |
| 0.914 (120 V, 100 W) | 14.06 V | 21.02 V | 1.50 |
| 0.941 (worst bus corner) | 14.47 V | 21.32 V | 1.47 |
| 0.9597 (clamp) | 14.76 V | 21.53 V | 1.46 |

Two consequences:

1. **The regulation model is correct** — the estimator measures the *filtered*
   differential, and the 339 Hz midpoint filter (`C29`/`C30` across the 10 kΩ
   bottom resistor) removes the carrier, so what the firmware measures is the
   60 Hz fundamental. `drive RMS = m · Vbus / √2` is right. The carrier-average
   differential is exactly `m · Vbus`, and the 60 Hz fundamental is `M · Vbus`
   — both verified numerically.
2. **The outlet and the transformer see the whole waveform.** About 46 % of the
   drive's RMS is 20 kHz carrier, so the primary winding sees 21.3 V RMS where a
   60 Hz sine would put 14.5 V — 47 % more voltage stress and 20 kHz core loss.

The sketch's own loading arithmetic at `:1583-1593` is written as if the drive
were a sine: "the 160 VA part runs at 69 %", "150 W … 84 % of the transformer's
VA rating and 75 % of the 12 V winding's current rating". The *current* figure
is roughly right (the primary current is set by the load and stays sinusoidal:
~6.9 A RMS of the 13.34 A rating at 100 W, i.e. 52 %), but the *voltage* side
of the VA calculation is ~1.47× the sine case, and the "75 % of the winding's
current rating" figure is really ~85 %.

**Proposed change**

* State the waveform explicitly in the sketch header, in
  `PIE-v1.9-information.md` and in the bring-up procedure: the drive is a
  20 kHz unipolar PWM with a 60 Hz envelope.
* Re-derive the transformer's loading with the carrier included and lower
  `LOAD_LIMIT_W` accordingly.
* Correct the "69 %" / "75 %" figures.

## F6 — MEDIUM — The efficiency constant double-counts the transformer

**Where**: `V1.9.ino:1545-1546` and `:2007-2013`.

```c
#define ETA_BUCK_HBRIDGE   0.92f    // battery -> bus -> bridge -> transformer
...
float pBatt = vIn * iIn;
float pBus  = pBatt - P_AUX_WATTS;
return pBus * ETA_BUCK_HBRIDGE;
```

The chain is battery → boost (≈0.92) → bridge → transformer (**0.89**) →
outlet. Applying 0.92 to the whole chain over-states the outlet power by
about 12 %:

* the droop term `y = B_DROOP · pOut` is then ~12 % too large, so the estimate
  reads ~0.6 V low at 100 W and the regulator over-drives by that much
  (computed: `B·ΔP/V = 5.666 × 12.3/120 ≈ 0.58 V`);
* the "load too heavy" limit of 150 W of *estimate* is ~136 W of true outlet
  power — which, with the 1.47× carrier factor from F4, is ~200 VA of drive
  against a 160 VA transformer.

The code documents the 10 % power error and says it is "absorbed exactly by the
fitted B_DROOP" — true for the *droop* term, but the same error is what the
load limit is compared against, so it does not cancel there.

**Fix**: either state `ETA_BUCK_HBRIDGE` as the boost-and-bridge efficiency
only (0.92) and fold the transformer's 0.89 into `B_DROOP`'s derivation, or
apply both explicitly and re-derive `LOAD_LIMIT_W` against the real waveform
(F4). Update the comment either way — it currently says the estimate is "about
10 % high" when the number is about 12 %.

## F7 — MEDIUM — The bus run window tolerates only one out-of-range tick

**Where**: `V1.9.ino:1775-1790`.

```c
if (!ok) {
  if (wasValid) { wasValid = false; return true; }   // one-cycle grace
  return false;
}
```

The first out-of-range sample is ignored; the **second consecutive** one
faults. So a bus excursion of 20 ms (two control ticks) trips "bus voltage"
and stops the inverter. The comment says "Require the bus to be out of range
persistently; single-sample noise is ignored by checking again on the next
control tick", which reads as a two-sample debounce rather than a one-tick
grace.

The bus is exposed to a load-dump droop and to 120 Hz ripple, and the run
window (±1.5 V) is already wider than the modulation budget allows at full
load (the sketch says so at `:1610-1613`). Twenty milliseconds is thin.

**Fix**: make the grace 3–5 ticks (30–50 ms) and say which in both the sketch
and `PIE-v1.9-information.md`; or filter the bus reading before comparing.
The behaviour change needs the information document updated in the same change.

## F10 — LOW — The RMS comment implies 128 samples per mains cycle

`V1.9.ino:1628-1631` and `PIE-v1.9-information.md:436-439` describe a
"128-sample ring at a minimum 130 µs cadence (≈ 16.6 ms, about one mains
cycle)". The *buffer* holds 128 samples, but each ADS7128 channel is only
refreshed once per round-robin sweep (5 channels × 200 µs), so the ring
contains roughly **16.6 independent samples per mains cycle**, each repeated
about 7.7 times.

This turns out **not** to matter: because the window is within 0.16 % of one
mains cycle, the time-weighted mean of sin² over it is accurate, and the
computed RMS error is **0.00–0.16 %** (modelled over the sweep phase). The
estimator is sound. The comment should say *why* it is sound, because a reader
will otherwise assume 128 independent samples and draw the wrong conclusion
about the noise floor.

## F11 — LOW — Reverse current is invisible to the firmware

`IC1` is an INA240A2 with `REF1`/`REF2` both grounded, so its output is
referenced to ground and cannot go negative. The ADS7128 is unipolar. A
reverse current through `Rsense1` therefore reads as 0 A, and the
over-current trip (`IIN_TRIP` 20 A) cannot see it. The input-rail check
(11–14 V) would still refuse to arm with a reversed battery, so this is not a
stand-alone hazard, but it should be recorded.

## F12 — LOW — `adc_read()` busy-waits in the power loop

`V1.9.ino:1938-1943` calls `adc_read()`, which in the pico-sdk is a
`START_ONCE` plus a busy-wait on `ADC_CS_READY` (the conversion is 96 ADC
clock cycles, ≈0.8 µs). The wait is short, so it does not threaten the 20 kHz
PWM (the carrier runs from the ISR), but it is a spin in the power path every
100 ms. It also means the temperature reading is always fresh — no staleness
problem, which is worth stating since the sketch's comment says "TMP235 is
slow".

## Verified correct

These were checked and are sound; they are recorded so the next pass does not
re-open them.

**Dead time and modulation** — independently re-modelled tick by tick from the
peripheral's semantics (`tests/test_v19_pwm_waveform.py`):

* the 500 ns gap holds on **both edges of both legs**, across the whole
  modulation range and in the dynamic case where the sine is rewritten every
  carrier and the slices latch at different instants;
* no shoot-through at any modulation, including the clamp;
* the carrier average of the differential is exactly `m · Vbus`, and the 60 Hz
  fundamental of the drive is `M · Vbus`, i.e. RMS `M · Vbus/√2` — the model
  the droop estimator uses is **right** (F4 is about the carrier, not the
  model);
* the per-carrier sine step (0.0181 at the clamp) is below the 2·dt/T band
  (0.020) the phase-offset compares tolerate, and the slice-0 wrap ISR really
  is the only writer of the four compares.

**ADS7128 driver** — every register constant checked against TI SBAS868A:

| item | code | datasheet | |
| --- | --- | --- | --- |
| opcodes | 0x08 / 0x10 / 0x18 / 0x30 | Table 9 | ✔ |
| address | 0x10 | Table 2, R1 and R2 both DNP → `001 0000b` | ✔ |
| SYSTEM_STATUS / GENERAL_CFG / DATA_CFG / CHANNEL_SEL / RECENT_CH0_LSB | 0x00 / 0x01 / 0x02 / 0x11 / 0xA0 | Table 10 | ✔ |
| OSR_DONE | SYSTEM_STATUS bit 3 | Table 12 | ✔ |
| STATS_EN / CNVST | GENERAL_CFG bits 5 / 3 | Table 13 | ✔ |
| APPEND_STATUS | DATA_CFG bits 5:4, cleared by writing 0 | Table 14 | ✔ |
| channel selection | CHANNEL_SEL bits 3:0 = MANUAL_CHID | Table 24 | ✔ (the device powers up in Manual Mode, so this is the correct register) |
| result alignment | `(msb<<8\|lsb) >> 4` | Figure 25 frame A: the 12-bit result is left-justified in bits 15:4 | ✔ |
| reference | AVDD = 3.3 V, `code·3.3/4096` | transfer characteristic is 0…AVDD | ✔ |

The `STATS_EN` + `CNVST` + `RECENT_CHx` flow is the datasheet's own manual-mode
flow, and because the firmware's sweep is strictly sequential (convert → wait →
read → next channel) no new conversion can land between the LSB and MSB bytes
of the block read — the "both bytes belong to one conversion" property holds
without clearing `STATS_EN`.

**Temperature path** — the schematic settles it:

* the netlist shows `U8.2` and `U9.2` are `VOUT_2`, i.e. the **TMP235's
  analogue output**, not an I²C device on the MCU's ADC. The DBZ package's
  three pins are VDD / VOUT / GND, and TI's product data gives the transfer
  function as **10 mV/°C with 500 mV at 0 °C** — exactly the firmware's
  `(volts − 0.5)/0.01` (`V1.9.ino:1942`);
* the divider network matches the firmware's constants exactly: `R25`/`R26` =
  36.5 k/10 k (AIN0), `R27`/`R28`, `R29`/`R30`, `R31`/`R32` = 68 k/10 k
  (AIN1–3);
* `IC1` is an **INA240A2** (gain 50) across `Rsense1` (2 mΩ) → 0.1 V/A, which
  is what `INA240_V_PER_A` uses;
* `U10.7` (AVDD) and `U10.10` (DVDD) are both on 3v3 ✔.

**Regulation arithmetic**

* the droop closed form `V² − xV + y = 0` and the choice of the larger root are
  correct, and the discriminant guard is correctly *not* a fault trigger;
* the "output out of reach" fault is reachable and fires exactly where the
  comments claim: at the bottom of the bus band the raw drive limit exceeds the
  PWM clamp, so `clampBound` is true and the fault latches after 200 ms;
* the regulator's integral action cannot wind up (it is re-clamped to the drive
  limit every tick) and its closed-loop time constant is ≈0.23 s, comfortably
  slower than the 200 ms debounce, so a load step does not false-trip it;
* the RMS estimator's accuracy is 0.00–0.16 % (F10).

**Firmware structure**

* the gates are parked low as the very first thing in `powerBegin()`, on every
  fault (`setFault` → `stopBridge` → `parkGatesLow`), on disarm, on sleep, on
  BOOTSEL entry and on a very-long hold — and the very-long hold disarms
  *before* its 120 ms blocking delay;
* the bridge cannot start without an explicit arm, and arming is refused while
  a fault is latched or the sensors are not ready;
* over-current and over-temperature faults cannot be cleared from the UI (the
  `"over-"` prefix check), and clearing any other fault disarms and forces a
  fresh probe and a full sweep;
* the watchdog is fed in the boot sweep as well as in the loop, and the 2 ms
  I²C timeout is set before `Wire.begin()`;
* the V1.8 → V1.9 port is complete: the five-LED re-indexing covers the menu
  windowing, the brightness and speed bars, the binary score display and the
  Fireball game, and no array is indexed out of range for `NUM_LEDS` = 5.

## Test-coverage gaps

`tests/test_repo.py` is a source-text consistency check and
`tests/test_v19_model.py` is largely arithmetic on constants — neither
executes the firmware. The highest-risk behaviours with **no** coverage today:

1. **fault latching and clearing** — that `setFault` parks the gates, that
   `"over-"` faults refuse to clear, and that clearing disarms and forces a
   re-probe;
2. **arming** — that `powerSetArmed(true)` is refused with a fault latched or
   the sensors not ready, and that the bridge cannot start unarmed;
3. **the ADS7128 driver** — the register contract is now pinned by
   `tests/test_v19_protection_latency.py`, but the *sequence* (convert → wait →
   read → advance) and the failure paths are not;
4. **the droop estimator and the regulator** as a closed loop — that the
   estimated outlet settles on the target across the bus band and the load
   range, and that a load step does not trip the out-of-reach fault;
5. **the gate-parking path** — that every fault path ends with the four gate
   pins low.

The new files added by this audit are:

* `tests/test_v19_pwm_waveform.py` — an independent model of the PWM
  peripheral, the dead time, the drive model and the carrier ripple;
* `tests/test_v19_protection_latency.py` — the protection latencies and the
  ADS7128 register contract, including two *expected failures* that record the
  F1 gap.

## Bring-up checklist additions

Derived from the findings above; the existing list in `AGENTS.md` still stands.

1. **Scope the four gate-driver inputs** before the bus is energised: confirm
   the high and low side of each leg never go high together, and that the gap
   is ≥ 500 ns on both edges, at the modulation the target actually commands
   (m = 0.879–0.941), not only at the clamp.
2. **Scope the primary differential** at 100 W: confirm it is a 20 kHz PWM
   with a 60 Hz envelope and that its 60 Hz fundamental is 14.1 V RMS (the
   model), while its *total* RMS is ~21 V. This is the number F4 is about.
3. **Measure the outlet and record its 20 kHz content.**
4. **ADS7128 register-level check** (F2, F3): confirm `OSR_DONE` asserts with
   `OSR_CFG` = 0; confirm the W1C clear works with the chosen opcode; confirm
   `RECENT_CHn` tracks the voltage on `AINn` for every channel, one at a time.
5. **Confirm the ADS7128's AIN1 (bus) reading never clips** — the 25.74 V full
   scale against the actual 120 Hz bus ripple, which depends on the LM5122
   loop's rejection at 120 Hz and has not been measured.
6. **DC-offset test** (F1): inject a known DC offset into the primary and
   measure how long the firmware takes to react, against the 11–13 ms knee.
   Do this *before* relying on the trip.
